## 背景

写真を数十枚まとめてアップロードすると、API はすぐに「アップロード成功」を返し、サムネイルはバックグラウンドでゆっくり生成されます。これが開始状態の「ローカル階層の非同期」です。ジョブは api プロセスのメモリ内キューに並び、
worker プロセスが処理します。しかしリリースで api を再起動すると、待機中のジョブはすべて消えます。サムネイルは照合ジョブが数分単位で拾い直しますが、「アップロード成功」の通知メールは本当に失われます。
このカードではジョブを Amazon SQS に入れ、「ジョブが残っているか」と「どのプロセスが生きているか」を切り離します。

:::why
SQS 標準キューは少なくとも 1 回の配信です。受信されたメッセージはすぐには削除されず、可視性タイムアウトの間だけ他のコンシューマーから見えなくなります。worker が処理を終えてから削除します。
worker が途中で強制終了されると、メッセージはタイムアウト後に再び現れ、次の受信で処理が続きます。重複して実行された分は、アプリの重複排除テーブル `processed_jobs` が吸収します。
:::

## 比較実験の予告

### 突発的なアップロード + プロセスの強制終了（queue/upload-burst、必須）

- **SQS なし（memory ローカル階層）**：ジョブは api プロセスのメモリにしかありません。30 秒目に api を再起動すると、待機中と処理中のジョブが一緒に消えます。
- **SQS あり**：同じ突発的なアップロードで、30 秒目に worker を直接 `kill -9` します。削除されていないメッセージは可視性タイムアウト後に再び現れ、再起動した worker が処理を続けます。
- **どこで確認できるか**：比較レポートの失われたジョブ数（`biz.jobs_lost`）が 0 より大きい値から 0 になります。EC2 の CPU グラフはスパイクから平らな形に変わり、キューが空になるまでの時間は長くなります。
  レスポンスヘッダー `X-CloudAlbum-Path` は `queue=memory:queued` から `queue=sqs:queued` に変わります。
- **結果が予想と違う場合**：まず before と after の両方が worker 階層であることを確認します。次に、after で強制終了したのが api ではなく worker であることを確認します。

## プラットフォームモードについて

比較実験はワークベンチで実行します。30 秒目の障害（api の再起動、worker の `kill -9`）はランナーが SSM Run Command でラボ用インスタンスに送るため、ラボ用インスタンスにログインする必要はありません。
