## 背景

你批量上传几十张照片，接口很快返回“上传成功”，缩略图在后台慢慢生成——这是起始状态的“本地档异步”：任务排在 api 进程的内存队列里，
由 worker 进程处理。可一旦发布重启 api，排队中的任务就全部消失：缩略图靠对账任务分钟级找回，“上传成功”的通知邮件就真的丢了。
这张卡片把任务放进 Amazon SQS，让“任务还在不在”与“哪个进程还活着”脱钩。

:::why
SQS 标准队列是至少一次投递：消息被接收后不会立刻删除，而是在可见性超时内对其他消费者不可见；worker 处理完才删除。
worker 中途被杀，消息在超时后重新出现，由下一次接收继续处理；重复执行由应用的去重表 `processed_jobs` 吸收。
:::

## 对比实验预告

### 突发上传 + 进程被杀（queue/upload-burst，必做）

- **没有 SQS（memory 本地档）**：任务只在 api 进程的内存里，第 30 秒重启 api，排队与在途的任务一起消失。
- **有了 SQS**：同样的突发上传，第 30 秒直接 `kill -9` worker。未删除的消息在可见性超时后重新出现，重启后的 worker 接着处理。
- **你会在哪里看到**：对比报告中的丢失任务数（`biz.jobs_lost`）从大于 0 变为 0；EC2 的 CPU 曲线从尖峰变为平台，排空时间变长；
  响应头 `X-CloudAlbum-Path` 从 `queue=memory:queued` 变为 `queue=sqs:queued`。
- **如果结果不符合预期**：先确认 before 与 after 两次都是 worker 档；再确认 after 杀掉的是 worker 而不是 api。

## 平台模式说明

对比实验在工作台运行；第 30 秒的故障（重启 api、`kill -9` worker）由运行器经 SSM Run Command 投递到实验机，你不需要登录实验机。
