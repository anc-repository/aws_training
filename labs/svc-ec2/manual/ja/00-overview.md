## 背景

CloudAlbum の L0 は EC2 が 1 台だけです。Nginx、api、worker、SQLite、アップロードしたファイルはすべてこのマシン上にあり、アプリは AWS SDK を読み込まず、AWS API も一切呼び出しません。
「従来の単一サーバー構成」との最大の違いは、データ、機密情報、ローカル設定がすべて**独立したデータボリューム**にあること（`/etc/cloudalbum → /var/lib/cloudalbum/etc`）で、
ルートボリュームはいつでも作り直せます。それでも単一障害点であることに変わりはなく、インスタンスを止めればサイト全体が止まります。

:::why
このカードには「モジュールを有効にする」ステップがありません。ec2 は基盤モジュールだからです。ここでやるのは L0 の性質を見極めることです。何がインスタンスとともに消え、何が消えないのか、
どこがセキュリティの最低ラインなのか。この後のカードは、どれもこの土台の部品を 1 つずつ置き換えていきます。
:::

## 比較実験の予告

ec2 には「あり / なし」の比較実験がありません。このカードで確かめるのは L0 の性質で、従来の単一サーバーでのやり方と L0 のやり方を並べて比べます。

- **パブリックアドレス**：EIP がないと、停止して再起動したときにパブリック IPv4 が変わります。L0 は EIP を使うので、アドレスは変わりません（ステップ 5 で実際に試します）。
- **データと機密情報の置き場所**：ルートボリュームに置くと、インスタンスを作り直したときにデータが失われ、鍵も作り直されます。L0 では独立したデータボリュームに置きます（ステップ 3 で点検します）。
- **インスタンスメタデータ**：IMDSv1 ではどんな GET リクエストでもメタデータを読めます。L0 は IMDSv2 を強制しており、トークンなしでは 401 が返ります（ステップ 4）。
- **単一障害点**：インスタンスを止める＝サイト全体が使えなくなります。L0 も単一障害点であり、それこそがロードバランシング、オートスケーリング、バックアップのカードで解決する課題です。

## プラットフォームモードについて

ラボ用インスタンスにはプラットフォームの管理ロール（SSM の管理チャネル専用）が付いており、アプリ自身には AWS の ID がありません。ステップ 5 の停止中は、ラボ用インスタンスのターミナルとローカルのチェックに「想定内の中断」と表示されます。
