## このラボでできたこと

- トランザクションメールを SES で実際に送信しました。確認コードがあなたの受信箱に届きました。サンドボックスが未検証のアドレスを拒否したとき、アプリはありのまま失敗として記録しました。
- バウンスと苦情の戻り経路を作りました。設定セットのイベント送信先 → SNS → SQS のフィードバックキュー → worker で、ラボ用インスタンスは受信ポートを一切開けていません。
- 「新しいコメント」の外部へのファンアウトを SNS に任せました。1 回発行し、`userId` のフィルターポリシーで該当するユーザーのメールサブスクリプションに配信し、受信キューにもコピーします。worker が停止している間、メッセージはキューで待ちます。

## 全体の比較

| 指標 | 開始時 | 完了後 |
|---|---|---|
| 1 つのイベントの配信方法 | EC2 が EmailPort を 1 件ずつ呼び出す | 1 回発行し、SNS が配信 |
| 発行側の所要時間と人数の関係 | 比例して増える | ほぼ変わらない |
| ユーザーにメールが届くか | 届かない（outbox だけ） | 届く（サンドボックス期間中は検証済みのアドレスとメールボックスシミュレーターだけ） |
| 「誰が受け取るか」を決めるもの | アプリのコード | サブスクリプションフィルターポリシー（SNS 側） |
| チャネルの拡張 | アプリのコードを変更 | サブスクリプションを追加（SQS、Lambda、HTTPS、SMS など） |
| EC2 に必要な受信ポート | なし | なし（SNS → SQS、SES → SNS → SQS はどちらも worker が取得） |
| バウンスと苦情 | 存在しない | イベントが戻り、無効なアドレスへの必須でないメールを自動で止める |

## 試験ポイントの振り返り

- SNS のトピック、サブスクリプションのプロトコル、サブスクリプションフィルターポリシー（メッセージ属性 / メッセージ本文）、メールサブスクリプションの確認、raw メッセージ配信、サブスクリプション単位の DLQ。順序付きのファンアウトには SNS FIFO + SQS FIFO。
- SNS + SQS のファンアウトと SQS の競合消費の違い。コンシューマーの停止中にキューがメッセージをバッファリングする。キューポリシーの `aws:SourceArn`。
- SES の ID の検証（メールアドレス / ドメイン）、DKIM、SPF、DMARC。サンドボックスと本番アクセス（リージョンごと）。送信クォータとレート。
- SES の設定セットとイベント送信先。SNS + SQS で、AWS サービスの非同期イベントを受信ポートのないアプリに安全に届ける。
- SNS、SES、EventBridge の使い分け。EC2 はデフォルトで送信の 25 番ポートを制限している。
