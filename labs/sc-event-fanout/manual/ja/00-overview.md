## 背景

出発点は L0 です。誰かが写真にコメントすると、CloudAlbum はサイト内メッセージ（ベルの未読数）を 1 件書き込み、さらに EC2 が EmailPort を 1 件ずつ呼び出して、メール通知を有効にした人にメールを送ります。
しかし EmailPort はメールをローカルの outbox に書き込むだけです（`/me/outbox` でプレビューでき、ページには「本地实现，未真正发信」（ローカル実装、実際には未送信）と表示されます）。受信者やチャネルが増えるほど EC2 の仕事が増えるのに、
ユーザーには 1 通も届きません。バウンスや苦情など論外です。

このカードでは、まずトランザクションメールを **Amazon SES** で実際に送信し、バウンスと苦情を SNS → SQS でアプリに引き戻します。次に「新しいコメント」の外部へのファンアウトを **Amazon SNS** に任せます。
アプリは `userId` のメッセージ属性を付けて `Publish` を 1 回呼ぶだけで、誰が受け取るかはサブスクリプションフィルターポリシーが決めます。モジュール付属の SQS 受信キューは各イベントのコピーを受け取り、worker はそれをもとに記録を補います。

## なぜ組み合わせるのか

- **SNS は「1 回の発行、複数箇所への配信」を担当します**。サブスクリプションごとにコピーを受け取るので、受信者が増えても発行側の所要時間は変わりません。サブスクリプションフィルターポリシーは配信の前に実行され、
  各サブスクリプションは自分に関係するメッセージだけを受け取ります。今後 SMS、モバイルプッシュ、データ分析を追加するのも、サブスクリプションを 1 つ増やすだけです。
- **SQS はプッシュを信頼できるプルに変えます**。SNS → SQS のサブスクリプションがイベントをキューに入れ、worker がロングポーリングで消費するので、ラボ用インスタンスに受信ポートは一切不要です。worker が停止している間、メッセージはキューで待ちます。
  ここで使っているのは notification と email の 2 つのモジュールに**付属**するキューで、queue モジュールは有効にしていません。
- **SES はトランザクションメールを担当します**。確認コードやパスワードの再設定のように、個別化されメールアドレスの所有を証明する必要があるメールは、SES であなたの送信元 ID から送られます（DKIM 署名付き）。
  設定セットのイベント送信先が配信、バウンス、苦情のイベントを SNS に送り、それが SQS のフィードバックキューに入り、worker が配信状態を更新して、バウンスしたアドレスへの必須でないメールの送信を止めます。
- **よくある誤った組み合わせ**：SNS のメールサブスクリプションで確認コードを送る（同じプレーンテキストが全サブスクライバーに送られ、配信停止のフッターが付き、受信者は先にサブスクリプションを確認する必要がある）。1 つの SQS キューで「1 対多」を実現する
  （競合消費で、1 つのメッセージは 1 つのコンシューマーにしか渡らない）。EC2 で SMTP を動かして直接送信する（送信の 25 番ポートはデフォルトで制限され、送信者の評価もない）。SES のイベントをインスタンスの HTTPS エンドポイントにプッシュさせる
  （受信ポートの公開が必要）。サンドボックスを無視する（サンドボックス期間中は検証済みのアドレスとメールボックスシミュレーターにしか送れない）。

## 比較実験の予告

### 1 つのイベントの外部へのファンアウト（notification/fanout、必須）

- **開始時（db）**：コメントのイベントごとに EC2 が EmailPort を 1 件ずつ呼び出し（このカードの出発点では outbox に書き込みます）、コメントのリクエストの Server-Timing の `notification` 区間にはこれらの呼び出しが含まれます。
- **完了後（sns）**：同じコメントで、EC2 は `Publish` を 1 回呼ぶだけです。メールは SNS が送り、受信キューにも別にコピーが届きます。
- **どこで確認できるか**：レポートのサーバー側の配信記録のチャネルが `email` から `sns` + `sqs-copy` に変わります。経路ヘッダーは `notification=db:email` から `notification=sns:published` に変わります。

### サブスクリプションフィルター（notification/filter、必須）

`+u1` の写真にだけコメントを 1 件投稿します。サーバー側には `sns` が 1 行と `sqs-copy` が 1 行だけあり、メールボックスに届くのは受信者が `+u1` のメールだけです。
CloudWatch の `NumberOfNotificationsFilteredOut` が増えます。

### worker の停止（notification/worker-stop、必須）

ランナーが 5 秒目に worker を停止し、50 秒目に起動します。コメントはいつもどおり成功し、通知メールもいつもどおり届き、滞留するのは受信キューだけです。worker が復旧すると滞留が消費され、`sqs-copy` の記録がそろいます。

### SES のサンドボックス（email/sandbox、必須）

検証していないアドレスに送ります。サーバー側では `failed`、エラーは `MessageRejected`、経路セグメントは `email=ses:rejected` と記録されます。登録自体はいつもどおり完了し、
アプリが失敗したメールをこっそり「送信済み」に書き換えることはありません。

## 始める前に

- **SES の送信元 ID**（`ses-identity`）：受信できるメールアドレスです。ステップ 3 のデプロイ後、メールボックスで「Amazon Web Services – Email Address Verification Request」のリンクをクリックします。
- **通知用メールアドレス**（`notify-email`）：`+` エイリアスに対応したメールアドレスで、送信元 ID と同じでも構いません。2 人のテストユーザーはその `+u1`、`+u2` エイリアス、運用担当のサブスクリプションは `+admin` エイリアスを使います。
  このカードでは「AWS Notification - Subscription Confirmation」を約 3 通クリックします。迷惑メールに振り分けられやすいので注意してください。
- カードは最後まで SES のサンドボックスで完了し、本番アクセスは申請しません。プラットフォームが代わりに検証や確認のリンクをクリックすることはありません。

## プラットフォームモードについて

比較実験とシードスクリプトはワークベンチで実行します。worker の停止と起動はプラットフォームの管理チャネル（SSM）で行うため、SSH は不要です。
