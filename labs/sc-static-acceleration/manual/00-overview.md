## 背景

起点是“L0 + S3”：照片在东京的 S3 桶里，浏览器拿每次都不同的预签名 URL 直接下载缩略图；页面与 `/assets` 由 EC2 上的 Nginx 直出。
海外用户的每一个字节都要跨洲回到东京，而且 URL 每次都变，浏览器缓存几乎派不上用场。
这张卡片在桶前面加一个 CloudFront 分配：缩略图与前端资源从离用户最近的边缘返回，照片桶对公网保持完全关闭。

## 为什么组合在一起

- **S3** 提供耐久、无需预置容量的源；**CloudFront** 在边缘缓存并终止 TLS；**OAC** 让 CloudFront 以服务身份（SigV4）读取私有桶，
  所以桶可以保持“四项 BPA 全开”，桶策略用 `AWS:SourceArn` 只放行本分配、只放行 `variants/*`。
- 页面、`/assets` 与 `/api/*` 仍回源到实验机（8080 源站监听器 + `X-Origin-Verify`），媒体走 S3：一个分配、两个源站、按路径分流。
- **常见错误组合**：用 S3 静态网站端点作源（只支持 HTTP、不能用 OAC、桶必须公开）；用 OAI 读 SSE-KMS 对象（不支持）；
  用 S3 Transfer Acceleration 或 Global Accelerator 代替 CDN（都不缓存内容）。
- **本版范围**：自定义域名（Route 53 Alias）与 us-east-1 的 ACM 证书在 tls、dns 模块实现后补回，本版用 `*.cloudfront.net` 默认证书，相关考点放在小测与选读中。

## 对比实验预告

### 媒体加载（cdn/media-load，必做）

- **开始时**：每张缩略图都是一次到 S3 或 EC2 的请求，源站负载随访问量线性增长。
- **完成后**：只剩未命中的回源；同一张缩略图的第二次请求由边缘返回（`X-Cache: Hit from cloudfront`）。
- **你会在哪里看到**：对比报告中的源站请求数与出网字节；`/lab` 的 cdn 卡片“源站负载”面板；响应头 `X-Cache`、`Age`、`X-Amz-Cf-Pop`。
- **说明**：工作台与实验机同在东京，首字节时间差别很小；跨洲的差异在手册中讲解，不做多区域测量。

## 平台模式说明

分配从创建到部署完成需要几分钟到十几分钟；回收时分配要先禁用再删除，耗时较长，平台会单独提示进度。
