## 背景

出発点は「L0 + S3」です。写真は東京の S3 バケットにあり、ブラウザーは毎回異なる署名付き URL を受け取ってサムネイルを直接ダウンロードします。ページと `/assets` は EC2 上の Nginx が直接配信しています。
海外のユーザーの 1 バイト 1 バイトが大陸をまたいで東京まで戻らなければならず、しかも URL が毎回変わるため、ブラウザーのキャッシュはほとんど役に立ちません。
このカードではバケットの前に CloudFront ディストリビューションを置きます。サムネイルとフロントエンドの資産はユーザーに最も近いエッジから返され、写真のバケットはインターネットから完全に閉じたままです。

## なぜ組み合わせるのか

- **S3** は耐久性が高く容量の事前確保が不要なオリジンを提供し、**CloudFront** はエッジでキャッシュして TLS を終端します。**OAC** によって CloudFront はサービスの ID（SigV4）でプライベートバケットを読めるため、
  バケットは「BPA の 4 項目をすべて有効」のままにでき、バケットポリシーは `AWS:SourceArn` でこのディストリビューションだけ、`variants/*` だけを許可します。
- ページ、`/assets`、`/api/*` は引き続きラボ用インスタンス（8080 のオリジンリスナー + `X-Origin-Verify`）にオリジンリクエストし、メディアは S3 を使います。1 つのディストリビューション、2 つのオリジンで、パスによって振り分けます。
- **よくある誤った組み合わせ**：S3 の静的ウェブサイトエンドポイントをオリジンにする（HTTP のみ、OAC を使えず、バケットの公開が必要）。OAI で SSE-KMS のオブジェクトを読む（対応していない）。
  CDN の代わりに S3 Transfer Acceleration や Global Accelerator を使う（どちらもコンテンツをキャッシュしない）。
- **このバージョンの範囲**：カスタムドメイン（Route 53 Alias）と us-east-1 の ACM 証明書は、tls と dns のモジュールが実装された後に追加します。このバージョンでは `*.cloudfront.net` のデフォルト証明書を使い、関連する試験のポイントは小テストと参考資料で扱います。

## 比較実験の予告

### メディアの読み込み（cdn/media-load、必須）

- **開始時**：サムネイルの 1 枚 1 枚が S3 または EC2 への 1 回のリクエストで、オリジンの負荷はアクセス数に比例して増えます。
- **完了後**：残るのはミスによるオリジンリクエストだけです。同じサムネイルへの 2 回目のリクエストはエッジから返されます（`X-Cache: Hit from cloudfront`）。
- **どこで確認できるか**：比較レポートのオリジンのリクエスト数と送信バイト数、`/lab` の cdn カードの「源站负载」（オリジンの負荷）パネル、レスポンスヘッダー `X-Cache`、`Age`、`X-Amz-Cf-Pop`。
- **補足**：ワークベンチとラボ用インスタンスはどちらも東京にあるため、最初のバイトまでの時間の差はごくわずかです。大陸間の差は手順書で解説し、複数リージョンでの測定は行いません。

## プラットフォームモードについて

ディストリビューションの作成からデプロイ完了までは数分から十数分かかります。回収時はディストリビューションを無効にしてから削除するため時間がかかり、プラットフォームが進捗を別途表示します。
