## 背景

L0 のアプリは AWS API を一切呼び出しません。このカードから、アプリはインスタンスプロファイルを通じて IMDSv2 から**一時的な認証情報**を取得します。有効期間は時間単位で、EC2 が自動でローテーションし、ディスクには書かれません。
この後の storage、queue、cdn などのモジュールは、すべてこのステップを前提にしています。悪い例は長期のアクセスキー（`AKIA…`）をディスクに書くことで、期限切れにならず、スナップショット、バックアップ、ログとともに広がってしまいます。

:::why
**インスタンスにロールがあっても、アプリが使っているとは限りません。** プラットフォームモードでは、ラボ用インスタンスに最初から `CloudAlbumAppRole`（`AmazonSSMManagedInstanceCore` だけを含む、プラットフォームの管理チャネル）が付いています。
このカードの「なし」とは、アプリが `IAM_CREDENTIALS=none` で、このロールをまったく読まないことです。iam を有効にすると、`scripts/module` はロールに iam モジュール専用の読み取り専用ポリシーをアタッチし、
アプリがインスタンスロールを使うように切り替えます。この後はモジュールを 1 つ有効にするたびに、そのモジュールのカスタマー管理ポリシーを 1 つアタッチします。最小権限がモジュールとともに増減するわけです。
:::

## 比較実験の予告

### ID の確認（iam/whoami、必須）

- **なし（none）**：アプリは AWS API を呼び出せず、whoami は「認証情報なし」と報告します。
- **インスタンスロールあり（role）**：呼び出し元は `assumed-role/CloudAlbumAppRole/<インスタンス ID>` で、キーは `ASIA` で始まり、有効期限があります。
- **どこで確認できるか**：whoami のレポート、`/lab` の iam カード、CloudTrail のイベントにある `userIdentity` です。
- **悪い例（読むだけ）**：長期のキーは `AKIA` で始まり、有効期限がありません。漏えいしたらキーを無効にするしかなく、業務もそこで止まります。

## プラットフォームモードについて

プラットフォームモードの `enable iam` は `AppRoleMode=existing` で動きます。`CloudAlbumAppRole` とインスタンスプロファイルはプラットフォームのもので、モジュールは自分の読み取り専用ポリシーを作成してアタッチするだけです。
このカードでは従量課金や時間課金のリソースを作成しません。
