## 背景

L0 のアラームは worker プロセス内の**ローカルアラーム評価器**が判定します。評価器は 30 秒ごとに、LabMetricsStore がデータベースに書き込んだ 1 分ごとの集計とホストのサンプルを読み、
`/etc/cloudalbum/alerts.yaml` のルール（5xx の割合、p95、メモリ、データディスク、api のハートビート）に従って OK / ALARM を決めます。状態が変わると管理者にサイト内メッセージを書き込み、
EmailPort でメールを送ります。問題は、評価器が監視対象のアプリと同じマシンで動いていることです。worker が落ちれば誰も評価せず、インスタンスが落ちれば誰もアラームを出しません。
EC2 にはデフォルトでメモリのメトリクスもありません。

このカードでは、同じメトリクスを Amazon CloudWatch にもまとめて送信します（`cloudwatch = local + まとめて送信`。ローカル側はそのまま動きます）。
CloudWatch エージェントでメモリとディスクを補い、アラームは AWS 側で評価され、モジュール付属の SNS トピック `ops-alarms` でメールが届きます。

:::why
アラームの仕組みは監視対象から**切り離す**必要があります。ハートビートのメトリクスは 1 分に 1 点で、アラームは「データがない」ことを違反として扱います（`TreatMissingData=breaching`）。
プロセスが死んだりインスタンスが停止したりしてデータが欠けても、アラームはちゃんと ALARM になります。ローカル評価器にはこれができません。評価器自身も同じマシンの上にいるからです。
:::

## 比較実験の予告

### アラームまでの時間（monitoring/time-to-alert、必須）

- **CloudWatch なし**：ローカル評価器は 30 秒ごとに動き、数秒から数十秒で ALARM になります。届け先はサイト内メッセージと outbox です。
- **CloudWatch あり**：同じ 5xx でも、CloudWatch のアラームは 1 分の期間 × 5 個中 3 個のデータポイントが必要で、さらに 60 秒ごとのまとめ送信とメトリクスが現れるまでの遅延が加わるため、分単位になります。
- **どこで確認できるか**：レポートの `biz.local_detect_sec` と `biz.cw_detect_sec`。どちらもサーバー側で記録された状態変化の時刻（ローカルの `alert_events`、
  CloudWatch のアラーム履歴）で、クライアントが見た応答ではありません。
- **結果が予想と違う場合**：CloudWatch 側でアラームが出ないときは、まず monitoring が「正常」か（送信が遅れていないか）を確認し、次に実験の時間が十分かを確認します。

### 停止（monitoring/kill-test、必須）

- **CloudWatch なし**：api と worker を止めた 5 分間、ローカル評価器は完全に沈黙し、アラームは 1 件も出ません。
- **CloudWatch あり**：同じようにサービスを止めると、`app-heartbeat` が 3～4 分後に ALARM になり、メールはいつもどおり届きます。
- **どこで確認できるか**：`biz.local_alerts_during_outage`（0 になるはず）と `biz.cw_heartbeat_alarm`。メールボックスの ALARM メール。

## プラットフォームモードについて

比較実験はワークベンチで実行します。サービスを止める障害スクリプトは SSM Run Command でラボ用インスタンスに送られる（`--fault-via ssm`）ため、ラボ用インスタンスにログインする必要はありません。
任意の「インスタンスの停止」ではプラットフォームの管理チャネルが数分間オフラインになります。ステップで想定内の中断を宣言しているため、画面には障害ではなく「想定内の中断」と表示されます。
