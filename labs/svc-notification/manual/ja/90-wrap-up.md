## このラボでできたこと

- 外部への通知を「EC2 が 1 通ずつ送る」方式から 1 回の SNS Publish に置き換え、メールサブスクリプションとモジュール付属の SQS 受信キューにファンアウトしました。
- サブスクリプションフィルターポリシーで各ユーザーが自分に関係する通知だけを受け取るようにし、CloudWatch でフィルターで除外された配信を確認しました。
- メールサブスクリプションの確認の流れと、worker が停止しても SNS の配信は続き、受信キューだけが滞留することを確認しました。

## 試験ポイントの振り返り

- SNS + SQS のファンアウトと SQS の競合コンシューマーの違い。サブスクリプションのプロトコル（HTTP/S、Email、SQS、Lambda、SMS、モバイルプッシュ、Firehose）。
- サブスクリプションフィルターポリシー（メッセージ属性 / メッセージ本文）。メールサブスクリプションには確認が必要。raw メッセージ配信。プロトコルごとの配信の再試行とサブスクリプション単位の DLQ。
- 順序と重複排除が必要なファンアウトには SNS FIFO + SQS FIFO。
- キューポリシーとトピックポリシーの `aws:SourceArn` / `aws:SourceAccount`。SSE-KMS のトピックとサービスプリンシパルへの許可。
- SNS、SES、EventBridge の使い分け：ブロードキャストのサブスクリプション、トランザクションメール、イベントの内容に基づくルーティング。
