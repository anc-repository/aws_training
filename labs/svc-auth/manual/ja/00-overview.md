## 背景

L0 のサインインはすべて EC2 が実装しています。argon2id によるパスワードハッシュ、ES256 の JWT、メールアドレスの確認、ロック、パスワードの再設定、任意の TOTP。どれも自分で書き、自分で保守し、リスクも自分で負うコードです。
Amazon Cognito User Pool を有効にすると、パスワードと認証フローは AWS に任されます。ブラウザーは Amplify を通じて User Pool と直接やり取りし、EC2 はパスワードに触れず、
User Pool が公開する JWKS を使ってローカルでアクセストークンを検証するだけになります。

:::why
**認証は外部に任せても、責任がすべて移るわけではありません。** パスワードハッシュ、ロック、MFA は AWS の担当です。しかし、アプリクライアントでユーザーにどの属性の書き換えを許すか、トークンの検証でどのクレームを確認するか、
サインアウト後に古いトークンがいつまで使えるかは、依然として私たちが設計で決めることです（責任共有モデル）。
:::

## 比較実験の予告

### 機能マトリクスと総当たり攻撃（auth/feature-matrix、auth/brute-force、before は必須）

- **Cognito なし（local）**：機能マトリクスには、ローカルで実装した登録、確認、ロック、TOTP が並びます。パスワードを続けて間違えると、401 → 423（ロック）/ 429（レート制限）の順に返ります。
- **Cognito あり**：MFA、パスワードの再設定、一時的なロック、フェデレーションサインインはすべて User Pool が提供します。トークンは Cognito が RS256 で署名します。
- **どこで確認できるか**：before の実験レポート、有効化後の `/api/capabilities` とプローブ用エンドポイント、User Pool とアプリクライアントの設定です。
- **補足**：この版では、after 側の比較はチェックと観察で行います（実験スクリプトの Cognito サインインには `USER_PASSWORD_AUTH` が必要ですが、このモジュールのクライアントは SRP しか許可していません）。

## プラットフォームモードについて

Cognito を有効にすると、`scripts/module` がワークベンチであなたの権限でフック `cognito-passwords` を 1 回実行し、開始状態で用意したテストアカウントを「確認済み・パスワード既知」にします。
パスワードはプラットフォームのパラメーターにだけ保存され、手順書やチェックの証拠には現れません。新しいアカウントの登録には受信できるメールアドレスが必要です。Cognito の確認コードは実際に送信されます。
