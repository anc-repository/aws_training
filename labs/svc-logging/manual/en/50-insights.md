Produce a few more 5xx, then aggregate them with Logs Insights in the console and find the metric generated by the metric filter.

1. On the workbench, run the load from before again (without uploading, just to produce 5xx; the fault clears automatically after 120 seconds):

```bash {runsOn=workstation}
npm run exp -- logging --label after --scenario query-compare
```

:::method{kind=console default}
2. CloudWatch → **Logs Insights** → in the "Queries" drop-down, choose the saved query `cloudalbum-{{ session.env }}/5xx-by-route` (log group
   `/cloudalbum/{{ session.env }}/nginx`), set the time range to "Last 1 hour" and run it. Look at the statistics below the results panel: records matched, records scanned and bytes scanned.
3. CloudWatch → **Metrics** → All metrics → namespace `CloudAlbum/Logs` → find `Nginx5xx` and graph it with "Sum" and a 1-minute period.
:::

:::wait{typical=5 max=10}
Metric filters match at ingestion: the metric appears in the list only after the first line with status ≥ 500 matches, which usually takes a few minutes.
:::

:::expected
The errors from `/api/lab/now` match the 5xx count in the report; the `Nginx5xx` metric has data points.
:::

:::saa{domain=resilient confusable="指标过滤器 vs Logs Insights"}
Metric filters only apply to logs ingested **after they are created** and are not retroactive; to count historical data, use Logs Insights (billed by data scanned).
Metrics generated by metric filters can drive alarms directly (svc-monitoring).
:::

::checks
