## 背景

L0 のログは EBS データボリューム上にしかありません。api と worker は pino で JSON 行を `/var/lib/cloudalbum/logs/api.log`、`worker.log` に書き、Nginx は
`nginx-access.json` に書きます。問題を調べるには、このインスタンスにログインしてファイルを 1 つずつ grep するしかありません。インスタンスが複数あれば 1 台ずつ見ることになり、インスタンスが置き換えられるとログも消え、Lambda のログはそもそもローカルにありません。
このカードでは、アプリに**同じ**構造化ログを Amazon CloudWatch Logs へまとめて送らせます。ローカルファイルへの書き込みも続けるので、ロールバックしてもデータの欠落はありません。

:::why
EC2 上でファイルに書かれたログは、自動では CloudWatch Logs に入りません。アプリ自身が `PutLogEvents` を呼ぶか（このモジュールの既定の sdk 方式。api と worker が
2 秒ごとにまとめて送信し、worker は Nginx のアクセスログも転送します）、CloudWatch エージェントがファイルを収集するか（任意のステップ）のどちらかです。Lambda のログは常に自動で入ります。
:::

## 比較実験の予告

### 同じクエリを両側で並べて実行（logging/query-compare、必須）

- **なし（ローカルファイル）**：まず共有の障害注入 API で約 20% のリクエストに 503 を返させ、「ルートごとの 5xx の集計」と「リクエスト ID での検索」を行います。インスタンス上で現在のファイルと `.1` を
  末尾から走査するしかなく、対象はこのマシンの直近 2 日分だけです。
- **CloudWatch Logs あり**：同じ 2 つのクエリにもう 1 つの側が加わります。FilterLogEvents で正確に検索し、Logs Insights で集計して**スキャンしたバイト数**（課金の基準）を報告します。
- **どこで確認できるか**：比較レポートの両側の 5xx の件数、所要時間、スキャンしたバイト数。両側の件数は、クライアントが受け取った 503 の数と一致するはずです。

### 取り込みの遅延（logging/ingest-lag、必須）

- **CloudWatch Logs あり**：20 件のリクエストが完了してから CloudWatch で検索できるようになるまでの時間です。サーバー側の証拠は各ログの `ingestionTime − timestamp` です。
  ローカルファイルなら即座に見えます。

## プラットフォームモードについて

比較実験はワークベンチで実行します。クエリはアプリの `GET /api/lab/logs`（管理者のみ）を通じてインスタンスロールで実行されます。受講者の ID は、コンソールで Logs Insights を見るためだけに使います。
`/atl-recordings/terminal-sessions` はプラットフォームのターミナルの録画用（任意）のロググループで、CloudAlbum のものではなく、このカードでは使いません。
