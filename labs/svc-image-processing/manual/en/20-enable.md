---
step: enable
---

Wire in Lambda: `scripts/module` packages `lambdas/image-thumbnail` (esbuild + sharp for linux-arm64), uploads it to the toolchain bucket,
deploys the function, the log group, the asynchronous invocation configuration, the EventBridge rule and the failure and result queues, restarts the worker and then api, and finally runs an end-to-end probe.

:::method{kind=script default}
Preview the changes first:

```bash {runsOn=workstation}
scripts/module enable image-processing --param ResultChannel=queue --dry-run
```

When you are happy with them, run it:

```bash {runsOn=workstation}
scripts/module enable image-processing --param ResultChannel=queue
```
:::

:::wait{typical=4 max=15}
Packaging, uploading, deploying and the end-to-end probe. When it is done, upload 3 photos in the app preview so the platform sees the real Lambda processing path.
:::

:::expected
image-processing is Healthy; the path header of upload requests contains `image-processing=lambda:async`; the badge on the photo details says "缩略图由 AWS Lambda 生成" (thumbnail generated by AWS Lambda).
:::

:::why
**Why a result queue for the write-back rather than an HMAC callback?** A callback needs Lambda to reach the lab instance from the internet (DEP-021 marks the module degraded, and an inbound port must be open to the internet);
with a result queue, EC2 long-polls on its own, no inbound traffic is needed, and results wait in the queue even while the lab instance is down. For the HMAC callback design, see the module docs (further reading).
:::

::checks
