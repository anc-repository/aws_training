## このラボでできたこと

- サムネイルの生成を EC2 上の sharp から S3 → EventBridge → Lambda に移しました。アップロード完了の API に残ったのはデータベースの更新 1 回だけで、EC2 の CPU はアップロード量に左右されなくなりました。
- 非同期呼び出しの再試行、イベントの最大有効期間、失敗時の送信先を読み解き、恒久的なエラーと一時的なエラーを区別しました。
- 自分の手で「緊急ブレーキ」を一度かけ、それが解除されていることを確認しました。

## 試験ポイントの振り返り

- Lambda の 3 種類の呼び出し（同期、非同期、イベントソースマッピング）。非同期呼び出しの再試行（0～2 回）、イベントの最大有効期間、Destinations と DLQ。
- S3 イベント通知 vs EventBridge vs SNS のファンアウト。コレオグラフィーとオーケストレーション。入力と出力を分けて再帰を防ぐこと。
- 予約済み同時実行とプロビジョニングされた同時実行、アカウントの同時実行クォータ。コールドスタートと `Init Duration`。メモリと CPU は比例し、arm64 はコストパフォーマンスがよいこと。
- 15 分のタイムアウト、`/tmp`、デプロイパッケージとレイヤー / コンテナイメージ。Lambda は EBS にアクセスできないため、状態は外に出す必要があること。
