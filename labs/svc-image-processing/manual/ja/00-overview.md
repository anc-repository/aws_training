## 背景

L0 のサムネイルは「アップロード完了」のリクエストの中で sharp が同期的に生成しています（inline、同時実行数 2）。200 枚を一括アップロードすると、リクエストはセマフォで順番待ちになり、2 つの vCPU が使い切られ、
タイムラインの閲覧まで遅くなります。キューの最後のほうのリクエストは Nginx に 504 で打ち切られることさえあります。このカードでは、元画像が S3 に置かれた瞬間に EventBridge が Lambda を非同期で呼び出してサムネイルを生成し、
EC2 は結果をデータベースに書き戻すだけになります。

:::why
Lambda はラボ用インスタンスの EBS も SQLite も読めません。計算を Lambda に任せたら、入力は S3 になければならず、結果はネットワーク経由で書き戻す必要があります。
そのため開始状態ではすでに storage(s3) が用意されており、書き戻しにはこのモジュール付属の結果キューを使います（インバウンドのトラフィックは一切不要です）。
:::

## 比較実験の予告

### 一斉アップロード（image-processing/upload-burst、必須）

- **Lambda なし（inline）**：complete API の所要時間＝ sharp の処理時間で、同時実行数 20 では秒単位になります。EC2 の CPU は使い切られます。
- **Lambda あり**：complete はデータベースを 1 回更新するだけで、数十ミリ秒程度です。EC2 の CPU はほぼ平らな線になり、サムネイルの大半は数秒で準備できます。
- **どこで確認できるか**：比較レポートの `POST /api/photos/complete` の p95、`host.cpu.p95`、`biz.photo_time_to_ready.p95`、
  そしてレスポンスヘッダー `X-CloudAlbum-Path` が `image-processing=inline` から `image-processing=lambda:async` に変わることです。
- **期待どおりにならないとき**：after の実行時に image-processing のドライバーが lambda で、状態が正常か確認してください。最初の写真にはコールドスタートが含まれるため、準備完了までの時間が長めになります。

### 失敗の経路（image-processing/failures、必須）

壊れた JPEG は恒久的なエラーです。関数はそのまま FAILED を書き戻し、再試行もせず、失敗キューにも入れません。

## プラットフォームモードについて

比較実験はワークベンチで実行します。関数のデプロイパッケージは `scripts/module` がパッケージングし、プラットフォームが事前に作成したツールチェーンのバケットにアップロードします。パッケージングのツールをインストールする必要はありません。
