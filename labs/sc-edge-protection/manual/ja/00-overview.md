## 背景

アルバムの公開から 1 か月、ログイン API には毎日何万回ものクレデンシャルスタッフィングが届き、アクセスログは `/wp-login.php` や `/.env` のようなスキャンだらけです。出発点は L0 で、入口はラボ用インスタンスの Elastic IP、
防御はインスタンス上の Nginx だけです。`limit_req` によるレート制限、数個の正規表現、そして `denylist.conf` です。これらで一部は防げますが、**悪意のあるリクエストはどれもすでに EC2 に届いており**、
インスタンスの接続、TLS、帯域を消費しています。

このカードでは L0 から出発し、3 つのことを自分の手で行います。インスタンスの前に CloudFront ディストリビューションを作り、直接アクセスの入口を管理者 IP にだけ残すこと。us-east-1 に Web ACL を作ってディストリビューションに関連付け、
マネージドルールグループをまず Count で誤検知を観察してから Block に切り替えること。最後に、オリジンのログで「ブロックされたリクエストが EC2 にまったく届いていない」ことを証明することです。

## なぜ組み合わせるのか

- **WAF には付ける先の入口が必要です**。EC2、Elastic IP、NLB には関連付けられず、CloudFront、ALB、API Gateway REST API などのリソースにしか付けられません（DEP-006）。
  このカードでは CloudFront を選びます。TLS の終端と WAF の検査がどちらもエッジで行われ、ブロックされたリクエストは東京リージョンに入らず、時間課金のロードバランサーも不要です。
- **CLOUDFRONT スコープは us-east-1 にあります**。Web ACL、IP セット、WAF のロググループはすべて us-east-1 に作られ（スタック `cloudalbum-{{ session.env }}-waf-edge`）、
  アプリのある ap-northeast-1 とは別です。
- **オリジンをロックして初めて意味があります**。ラボ用インスタンスの 80/443 は管理者 IP にだけ開き、8080 のオリジンリスナーは CloudFront のマネージドプレフィックスリストだけを許可し、さらに Nginx がこのディストリビューションしか知らない
  `X-Origin-Verify` を検証します。WAF だけを有効にしてオリジンをロックしなければ、攻撃者は Elastic IP に直接アクセスしてすべてのルールを迂回できます（DEP-018）。
- **Shield と GuardDuty はそれぞれ別の層を担当します**。Shield Standard はすべての CloudFront ディストリビューションに自動で適用され、一般的なネットワーク層とトランスポート層の DDoS を防ぎます。
  GuardDuty は CloudTrail、VPC フローログ、DNS ログを分析し、検出結果を生成するだけでブロックはせず、HTTP の内容も見ません。
- **よくある誤った組み合わせ**：プレフィックスリストだけでオリジンをロックする（他人のディストリビューションも同じアドレス範囲から来る）。Web ACL を ap-northeast-1 に作ってからディストリビューションに関連付けようとする。
  マネージドルールを Count で観察せずにいきなり Block にする（CRS が写真のアップロードの大きなリクエストボディを誤ってブロックする）。クレデンシャルスタッフィング対策に Shield Advanced を購入する。

## 比較実験の予告

すべての攻撃は自分のアカウントのラボ用インスタンスだけを対象にし、短いラウンドで、しきい値をわずかに上回る低いレートを保ち、AWS のペネトレーションテストのポリシーに従ってください（公式ドキュメントを確認してください）。

### レート制限（waf/flood、必須）

- **開始時**：ワークベンチからしきい値をわずかに上回るレートで `POST /api/auth/login` に送ると、Nginx の `limit_req` はほぼ即座に 429 を返しますが、どのリクエストもインスタンスに届いています。
- **完了後**：同じ攻撃を CloudFront に向けると、レートベースのルールはウィンドウで集計され検知に遅延（数十秒）があり、ブロックされたリクエストはオリジンに届きません。
- **どこで確認できるか**：レポートのブロックの割合と最初にブロックされた時刻。サーバー側の証拠は、オリジンのアクセスログにおける今回の nonce の件数（`/api/lab/waf/origin`）で、クライアントが見たレスポンスヘッダーではありません。

### 攻撃ペイロードの識別（waf/payloads、必須）

同じ公開の WAF テスト用ペイロード一式（SQL インジェクションとそのエンコードのバリエーション、ディレクトリトラバーサル、XSS、Log4Shell のプローブ、スキャナーの User-Agent）を 2 つの経路それぞれに送ります。
Nginx の数個の正規表現は、二重エンコード、大文字小文字、コメントのバリエーションを見逃します。結果の `caughtOnlyByWaf` に、Nginx が見逃してマネージドルールグループがブロックしたバリエーションが並びます。

### 誤検知（waf/false-positive、必須）

Count モードで、正当だが「怪しい」リクエストを 2 つ送ります。8 KB を超えるリクエストボディと、`SELECT * FROM` を含む普通のテキストです。どのルールが一致するか、
そしてこのモジュールが CRS の `SizeRestrictions_BODY` を Count に上書きしている理由を確認します。

### waf/bypass を使わない理由

ワークベンチのパブリックな送信元は、あなたが設定した管理者 IP そのものなので、ワークベンチから 80 番ポートを調べれば必ず到達できます。このカードでは代わりにサーバー側の証拠で「迂回できない」ことを示します。ラボ用インスタンスとオリジンのセキュリティグループのルール、
ラボ用インスタンス自身から検証ヘッダーなしで 8080 にリクエストすると 403 になること、そして CloudShell（管理者 IP ではない）から直接アクセスしたときのタイムアウトです。

## プラットフォームモードについて

- `scripts/module enable waf` は受講者の ID で us-east-1 にスタック `cloudalbum-{{ session.env }}-waf-edge` をデプロイし、`WebAclArn` を cdn スタックに注入して、ディストリビューションを再デプロイします（数分）。
- オリジンをロックすると、プラットフォームの Lambda はラボ用インスタンスのパブリックな入口にアクセスできず、直接アクセスのプレビューもセキュリティグループで遮られます。アプリのプレビューはディストリビューションのドメイン名に切り替わり、以降の直接アクセス系のチェックはすべてラボ用インスタンス自身から行われます。
- `WAF_LAB_ALLOW_CIDR` は空のままでなければなりません。これは Allow アクションで、列挙したアドレスにすべてのルールをスキップさせてしまいます。
