CTO の最後の質問は「Shield Advanced を買ったり GuardDuty を有効にしたりする必要があるのか」です。コンソールで Shield のページを見て（**見るだけで、サブスクライブしないでください**）、次の表と照らし合わせて答えてください。

::console-link[WAF と Shield のコンソールを開く]{link=wafv2.webAcls}

| 層 | サービス | このカードでの状態 | 担当すること |
|---|---|---|---|
| レイヤー 3/4 の境界 | セキュリティグループ、NACL | 締めた（ステップ 3、4） | IP とポートで許可する。セキュリティグループには許可ルールしかない |
| レイヤー 3/4 の DDoS | Shield Standard | 自動で有効、追加料金なし | SYN フラッド、UDP リフレクションなど一般的なネットワーク層とトランスポート層の攻撃 |
| 大規模な DDoS への対応 | Shield Advanced | サブスクライブしない | 年単位のサブスクリプション。DDoS レスポンスチーム、スケールアウトの費用の保護、より詳しい攻撃の可視化 |
| レイヤー 7 のフィルタリング | AWS WAF | 有効（ステップ 5～7） | レートベースのルール、マネージドルールグループ、IP セット、地理的一致。ブロックできる |
| 脅威検出 | GuardDuty | このバージョンでは有効にしない | CloudTrail、VPC フローログ、DNS ログを分析。検出結果を生成するだけでブロックせず、HTTP の内容も見ない |
| 複数アカウントの一元管理 | Firewall Manager | 対象外 | 組織内で WAF のルール、Shield Advanced の保護、セキュリティグループのポリシーを一元的に配布する |

:::warning
Shield Advanced は年単位のコミットメントで課金されます。コンソールで誤ってサブスクライブした場合は、すぐに AWS に連絡して対処してください。プラットフォームでは回収できません。
:::

:::why
**クレデンシャルスタッフィングは DDoS ではありません。** クレデンシャルスタッフィングは低レートで、普通のログインのように見えるレイヤー 7 の悪用です。Shield は扱わず、WAF の `rate-login` とマネージドルールグループ（必要なら Bot Control）こそが適した道具です。
GuardDuty が解決するのは別の種類の問題、つまりインスタンスが侵害された後の外部へのスキャン、マイニングプールへの接続、異常な API の呼び出しです。WAF を補完するもので、置き換えるものではありません。
:::

:::expected
次のことを説明できるようになっています。Shield Standard はこのディストリビューションにすでに自動で適用されていること、Shield Advanced はこのシナリオのクレデンシャルスタッフィングとは関係ないこと、GuardDuty にはステップ 2、9 のペイロードは見えず、ブロックもしないことです。
:::

::checks
