## このラボでできたこと

- L0 から CloudFront ディストリビューションを作り、同じ有効化の中で直接アクセスの入口を管理者 IP にだけ残しました。オリジンの 8080 は CloudFront のプレフィックスリスト + `X-Origin-Verify` だけを受け付けます。
- us-east-1 に CLOUDFRONT スコープの Web ACL を作りました。ログインと全体の 2 つのレートベースのルール、IP セット、4 つの AWS マネージドルールです。まず Count で誤検知を観察し、その後 Block に切り替えました。
- オリジンのログの nonce の件数で、WAF にブロックされたリクエストが EC2 にまったく届いていないことを証明しました。セキュリティグループのルールと CloudShell からの直接アクセスで、攻撃者がエッジを迂回できないことを証明しました。

## 全体の比較

| 指標 | 開始時 | 完了後 |
|---|---|---|
| 悪意のあるリクエストを処理する場所 | EC2 上の Nginx | CloudFront のエッジの WAF |
| 攻撃中にオリジンが受け取るリクエスト | 攻撃に比例して増え、拒否されたものもすべてインスタンスに届く | ブロックされたリクエストはオリジンに届かず、オリジンの負荷はほぼ安定 |
| 防御を迂回する経路 | 迂回すべき「防御層」が存在しない | 80/443 は管理者 IP にだけ開き、8080 はこのディストリビューションだけを受け付ける |
| 悪意のあるペイロードの識別 | 数個の手書きの正規表現で、エンコードのバリエーションを見逃す | マネージドルールグループが継続的に更新される |
| 複数インスタンスでの上限 | インスタンスごとに別々に数える | Web ACL が全体で数える |
| DDoS の基本的な防御 | なし | Shield Standard が自動で有効 |
| 可観測性 | Nginx のログの集計 | サンプリングされたリクエスト、CloudWatch メトリクス、WAF のログ（us-east-1） |

## 試験ポイントの振り返り

- WAF の関連付け先（CloudFront、ALB、API Gateway REST API、AppSync、Cognito User Pool など）と関連付けられないリソース（EC2、Elastic IP、NLB）。CLOUDFRONT スコープは us-east-1。
- Web ACL、ルールグループ、マネージドルールグループ、レートベースのルール、IP セット、地理的一致。Count モード、ルールアクションの上書き、スコープダウンステートメントと WCU。
- オリジンの保護：CloudFront のマネージドプレフィックスリスト + カスタムリクエストヘッダー。S3 オリジンには OAC。VPC オリジン（VPC Origin）ならオリジンにパブリックな入口がまったくなくなる。
- セキュリティグループ / NACL（レイヤー 3/4）と WAF（レイヤー 7）の役割分担。CloudFront の背後では `X-Forwarded-For` で実際のクライアント IP を得る。
- Shield Standard と Shield Advanced。Firewall Manager。GuardDuty は検出するだけでブロックせず、WAF を補完する。
