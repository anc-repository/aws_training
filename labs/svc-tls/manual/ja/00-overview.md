## 背景

L0 の 443 は User Data が生成した自己署名証明書（`CN=cloudalbum-l0`）を使っています。通信は暗号化されていますが、ブラウザーには「保護されていない通信」と表示され、クロスオリジンの fetch や Cognito のコールバックは失敗します。
AWS Certificate Manager には証明書を提供する方法が 2 つあります。**統合証明書**は CloudFront、ALB、API Gateway に付け、秘密鍵は ACM が管理し、エクスポートできず、自動で更新されます。
2026-07 からは ACM の **ACME エンドポイント**で、自己管理のサーバーに 45 日のパブリック証明書を発行できます。秘密鍵はインスタンス上に残り、certbot が更新します。

:::warning
**手動の前提作業：独自ドメイン**が必要で、その DNS に CNAME（ACME のドメイン検証または ACM の DNS 検証）と A レコード（ラボ用インスタンスの EIP を指す）を追加できなければなりません。ACM は IP、
`amazonaws.com`、`cloudfront.net` の名前には証明書を発行できません。このアカウントにそのドメインの Route 53 ホストゾーンがある場合は、`--zone-id` で検証レコードを自動作成できます。
ドメインがないとこのカードは完了できません。`scripts/module enable tls` はメッセージを表示して終了コード 2 で終わり、何もデプロイしません。
:::

:::saa{domain=secure}
**試験の結論**：ACM のパブリック証明書は EC2 に導入できず、統合サービスにしか付けられません。CloudFront で使う証明書は us-east-1 になければなりません。
**2026 年の新機能**：ACME エンドポイント + 事前承認された DNS ドメイン検証 + EAB で、証明書を自己管理のサーバーに導入できます。逆にこの種の証明書は CloudFront や ALB には付けられません。解答は試験の結論を基準にしてください。
:::

## 比較実験の予告

### 各入口の証明書（tls/inspect、必須）

- **ACM なし**：直接アクセスの `https://<EIP>/` の証明書は `CN=cloudalbum-l0` による自己署名で、チェーンは信頼されません。経路ヘッダーは `tls=selfsigned@nginx` です。
- **ACM あり**：ACME の分岐では、直接アクセスの証明書が Amazon によって発行され、SAN にあなたのドメインを含み、有効期間は約 45 日です。フォールバックの分岐では、CloudFront の代替ドメイン名で us-east-1 の統合証明書が見えます。
- **どこで確認できるか**：比較レポートの各入口の発行者、SAN、残り日数、`trustedEntries`。サーバー側の証拠は、ラボ用インスタンス上の tls 検知処理による `127.0.0.1:443`
  とのハンドシェイクの結果と `capabilities.https` です。
- **結果が予想と違う場合**：まず tls の状態の詳細を見ます。「签发者不是 Amazon」（発行者が Amazon ではない）とあれば、証明書のシンボリックリンクが切り替わっていないか、Nginx が reload されていません。

### 更新の演習（tls/renew-drill、ACME の分岐）

`certbot renew --dry-run` と `--force-renewal`：新しい証明書が Nginx に導入され、ACM の証明書の ARN は変わりません（同じ ACME アカウント、同じドメインと鍵アルゴリズム）。

## プラットフォームモードについて

このカードではプラットフォームの方式 B のプレビュー（Let's Encrypt IP 証明書）を無効にしており、プレビューは新しいタブで `http://<EIP>` を開きます。プラットフォームは開始前にアカウントの事前チェックで ACME エンドポイントが使えるかを判断し、
開始時のバリアント（現在：`{{ session.variant }}`）を選んでいます。`default` は ACME の分岐、`acme-off` は開始状態に CloudFront ディストリビューションが加わり、フォールバックの分岐を進みます。
