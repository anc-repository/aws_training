## 背景

L0 の「ファイアウォール」は EC2 上の Nginx です。`limit_req` によるレート制限と数個の正規表現で明らかな攻撃は止められますが、**悪意のあるリクエストはすべてインスタンスに届いており**、接続、TLS、ログ、帯域を消費します。
このカードでは **AWS WAF** を CloudFront に付け、エッジでマネージドルールとレートベースのルールによってブロックします。ブロックされたリクエストは EC2 にまったく届きません。前提はオリジンが**ロック**されていることで、そうでないと攻撃者は迂回できます。

:::why
WAF はレイヤー 7 で動作し、CloudFront、ALB、API Gateway REST API などにしか関連付けられず、EC2 / EIP / NLB には関連付けられません（DEP-006）。CLOUDFRONT スコープの
Web ACL、IP セット、ロググループはすべて **us-east-1** にあり、東京のアプリのリージョンとは別です。
:::

:::warning
攻撃スクリプトは自分のアカウントのリソースだけを対象にし、低いレート（短いラウンド）を保ち、AWS のペネトレーションテストのポリシーに従ってください（公式ドキュメントを確認してください）。`flood` を洪水攻撃のレベルまで上げないでください。
:::

## 比較実験の予告

### レート制限（waf/flood、必須）

- **AWS WAF なし（Nginx）**：1 つの送信元からしきい値をわずかに上回るレートで直接アクセスの入口に送ると、Nginx の `limit_req` がほぼ即座に 429 でブロックしますが、どのリクエストもインスタンスに届いています。
- **AWS WAF あり**：同じ攻撃を CloudFront に向けると、レートベースのルールはウィンドウで集計され検知に遅延（数十秒）があり、ブロックされたリクエストはオリジンに届きません。
- **どこで確認できるか**：`/api/lab/waf/origin` の nonce の件数。直接アクセスではすべてのリクエストがオリジンのログに数えられ、WAF でブロックされたリクエストはオリジンのログに入りません。
- **結果が予想と違う場合**：`WAF_LAB_ALLOW_CIDR` が空であること（空でないとラボ用インスタンスはすべてのルールをスキップします）、オリジンがロックされていてワークベンチには直接アクセスが開いていることを確認してください。

### 攻撃ペイロードの識別（waf/payloads、必須）

Nginx の数個の正規表現は、二重エンコード / 大文字小文字 / コメントのバリエーションで簡単に迂回されます。AWS マネージドルールグループのほうが識別に強いです。結果の `caughtOnlyByWaf` には、Nginx が見逃して WAF がブロックしたバリエーションが並びます。

### オリジンのロック（waf/bypass、必須）

ラボ用インスタンスの直接アクセスのポートと 8080 に直接リクエストします。ロックしていなければ直接アクセスで到達できます（WAF を迂回できる、DEP-018）。ロック後は直接アクセスが拒否 / タイムアウトし、8080 は `X-Origin-Verify` が一致しないため 403 を返します。

### 誤検知（waf/false-positive、必須）

正当だが「怪しい」リクエストです。大きなリクエストボディ（CRS の `SizeRestrictions_BODY` は Count に上書き済みなので通過するはず）と、SQL のキーワードを含む普通のテキスト（Block モードでは SQLi ルールに誤ってブロックされることがある）です。

## プラットフォームモードについて

`scripts/module enable waf` は us-east-1 に Web ACL を作成し、`WebAclArn` を cdn スタックに注入します（ディストリビューションの再デプロイに数分）。プラットフォームは、このセッションの waf モジュールのスタックで Web ACL があなたのものであることを確認します。
マネージドルールグループの Block が返すのは CloudFront の 403 で、アプリの経路ヘッダーは付きません。そのためブラウザーで見えるレスポンスヘッダーは観察用にとどめ、ブロックされた位置は**オリジンがリクエストを受け取ったかどうか**で判断します。
