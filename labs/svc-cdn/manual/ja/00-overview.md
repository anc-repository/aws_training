## 背景

アルバムは東京の 1 台の EC2 にデプロイされています。サムネイルも JS ファイルも、すべてこのマシンの Nginx が返します。海外のユーザーがアルバムを開くと、すべてのバイトが海をまたいで往復します。
アクセスが増えるほど、EC2 のネットワークとデータ転送（アウト）の料金も増えます。このカードでは EC2 の前に Amazon CloudFront を置き、同じコンテンツをユーザーに最も近いエッジロケーションから返します。
キャッシュにヒットすれば、オリジンにはまったく戻りません。

:::why
CloudFront のカスタムオリジンはドメイン名しか受け付けないため、ディストリビューションはラボ用インスタンスのパブリック DNS をオリジンにします。「あなたのディストリビューションだけ」がオリジンにアクセスできるよう、モジュールはラボ用インスタンスに CloudFront 専用の 8080 リスナーを開きます。セキュリティグループは CloudFront のマネージドプレフィックスリストだけを許可し、さらに Nginx があなただけが知っている `X-Origin-Verify` リクエストヘッダーを検証します。
:::

## 比較実験の予告

### オリジン負荷（cdn/media-load、必須）

- **CloudFront なし（EC2 から直接配信）**：ワークベンチがアルバムとサムネイルを読み込み続け、すべてのリクエストが EC2 の Nginx に届きます。
- **CloudFront あり**：同じ負荷をディストリビューション経由で送ります。キャッシュにヒットしたリクエストはオリジンに戻らず、EC2 が処理するのはミスした分だけです。
- **どこで確認できるか**：比較レポートでオリジンのリクエスト数（`server.origin`）と EC2 の送信バイト数（`host.net_tx_bytes`）が下がります。レスポンスヘッダー `X-Cache` がなかった状態から
  `Hit from cloudfront` になり、`X-CloudAlbum-Path` の `entry` が `nginx` から `cloudfront>nginx` に変わります。
- **期待どおりにならないとき**：まず after の実行に `--param target=cdn` を付けたか確認し、次にディストリビューションの状態が「デプロイ済み」になっているか確認します。

### 最初のバイトまでの時間と圧縮（cdn/ttfb、cdn/compression、任意）

ワークベンチとラボ用インスタンスはどちらも東京にあるため、最初のバイトまでの時間の差は小さく、参考程度です。圧縮の実験では、CloudFront 経由の JS と CSS に付く `Content-Encoding: br` を確認します。

## プラットフォームモードについて

このカードでは `scripts/module enable cdn` でディストリビューションを一括作成します（ルート S）。プラットフォームは、このセッションの cdn モジュールスタックからディストリビューションがあなたのものだと確認します。チェックの際はプラットフォーム自身がディストリビューションのドメインにリクエストし、
相手の IP が CloudFront のアドレス範囲に属することを確かめ、オリジンのログでリクエスト回数を数えます。そのため、ブラウザーで見えるレスポンスヘッダーは観察用であり、完了の根拠にはなりません。
