## 背景

L0 のタイムラインは毎回データベースに問い合わせます（`CACHE_DRIVER=none`）。タイムラインは典型的な「読み取りが多く書き込みが少ない」API で、同じ人のタイムラインは数十秒のうちに何度も読まれ、内容はほとんど変わりません。
キャッシュアサイド（cache-aside）では、まずキャッシュを読み、ミスしたらデータベースに問い合わせてキャッシュに書き戻します。書き込み時にはバージョン番号を増やし、古いキーが自然に使われなくなるようにします。
このカードではデフォルト VPC に単一ノードの Amazon ElastiCache（Valkey）を作り、複数のプロセスや複数のインスタンスで同じキャッシュを共有できるようにします。

:::why
キャッシュは**権威を持たない**ポートです。本当のデータはデータベースにあります。キャッシュに接続できないとき、アプリはミスとして処理し（fail-open）、リクエストは遅くなっても失敗せず、モジュールは degraded と表示されます。
つまり、キャッシュの故障がユーザーに見えるエラーになってはいけません。
:::

## 比較実験の予告

### タイムラインの読み取り負荷試験（cache/feed-read、必須）

- **キャッシュなし（none）**：タイムラインのリクエストごとに何回かデータベースへのクエリが実行されます。
- **ElastiCache あり**：ヒットすればリクエストあたりのデータベースへのクエリは 0 回です。after では `--ab` を付け、同じデプロイ内でリクエストごとに交互にキャッシュをバイパスするため、A / B の 2 グループを同じ時間帯で比較できます。
- **どこで確認できるか**：比較レポートの `client.timing.database.calls_per_request` とヒット率 `client.outcome_ratio.cache.hit`、
  レスポンスヘッダー `X-CloudAlbum-Path` の cache セグメントが `none` から `redis@elasticache:hit` / `miss` に変わることです。
- **期待どおりにならないとき**：SQLite は同じホスト上にありデータ量も少ないため、レイテンシーの差ははっきりしないことがあります。p95 だけでなく、リクエストあたりのクエリ回数を見てください。単一プロセスでは、プロセス内キャッシュ（memory）のヒットのほうがむしろ速くなります。

## プラットフォームモードについて

ElastiCache のノードは作成した時点から時間課金されます。比較実験はワークベンチで実行します。ワークベンチとラボ用インスタンスはどちらもデフォルト VPC にありますが、キャッシュに接続できるのはラボ用インスタンスだけです。ステップ 5 で実際に確かめます。
