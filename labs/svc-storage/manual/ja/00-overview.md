## 背景

このアルバムには EC2 が 1 台しかありません。元画像はすべて Nginx を通って Node プロセスに流れ込み、20 GiB のデータボリュームに書き込まれます。同じディスクには SQLite、ログ、ローカルバックアップもあります。
大勢のユーザーが同時に大きな画像をアップロードすると、EC2 のネットワーク（受信）と CPU がアップロードで埋まり、タイムラインの閲覧も遅くなります。ディスクがいっぱいになると、コメントの投稿（SQLite への書き込み）さえ失敗します。
このカードでは「写真の保存」を Amazon S3 に任せます。ブラウザーは署名付き URL を受け取ってファイルを S3 に直接送り、EC2 は署名だけを担当します。

:::why
署名付き URL は、アプリが自分の認証情報で「あるオブジェクトキー、ある操作、ある有効期間」に署名して作る URL です。ブラウザーはそれを使って S3 に直接 PUT し、バイトはアプリケーションサーバーを通りません。
S3 は署名を検証してからオブジェクトを受け取ります。署名付き PUT ではファイルサイズを制限できないため、アプリは「アップロード完了」の時点で `HeadObject` を使ってもう一度検証します。
:::

## 比較実験の予告

### 突発的なアップロード（storage/upload-burst、必須）

- **S3 なし（EBS + Node がディスクに書き込む）**：10 並列で 5 MB の画像をアップロードし続けると、バイトはすべてラボ用インスタンスのネットワーク（受信）と Node プロセスを通ります。
- **S3 あり**：同じ負荷テストで、ブラウザー（ランナー）が S3 に直接アップロードし、ラボ用インスタンスは URL を発行するだけです。
- **どこで確認できるか**：比較レポートでラボ用インスタンスのネットワーク受信バイト（`host.net_rx_bytes`）がアップロード量に応じて増えなくなります。同じ時間帯の `GET /api/feed` の p95 はほぼ変わりません。
  経路ヘッダーは `storage=local:write` から `storage=s3:presign` に変わります。
- **結果が予想と違う場合**：まず after の時点で storage のドライバーが s3 になっていることを確認します。次に 2 回の負荷テストのパラメーターが同じ（`--param fileMb=5`、`--duration 60s`）ことを確認します。
