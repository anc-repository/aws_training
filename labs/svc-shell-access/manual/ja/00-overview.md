## 背景

CloudAlbum で問題が起き、EC2 にログインしてトラブルシューティングする必要があります。L0 のやり方は SSH です。セキュリティグループで運用 IP に 22 番ポートを開け、秘密鍵の配布、ローテーション、紛失対策が必要です。後からわかるのは
「どの公開鍵がどの IP からログインしたか」だけで、ログイン後に何をしたかはわかりません。プラットフォームモードでは、ラボ用インスタンスの SSM Agent は「プラットフォームの管理チャネル」のためにすでにオンラインです。そのため、このカードで比較するのは
「SSM Agent があるかないか」ではなく、**運用担当者がどの経路でログインし、誰がログインでき、後から追跡できるか**です。

:::why
Session Manager の接続はすべて、インスタンス上の SSM Agent が**自分から外向きに**張ります（`ssm`、`ssmmessages` エンドポイントへの 443）。運用担当者は自分の IAM ID で
Systems Manager を中継して接続します。セキュリティグループはステートフルで戻りのパケットは自動で許可されるため、インスタンスに管理ポートの受信は一切不要です。各セッションは CloudTrail に記録され（誰が、いつ）、
セッション内のコマンドと出力はセッションログのロググループに書き込まれます。
:::

## 比較実験の予告

### ポートの調査（shell-access/probe-port、必須）

- **なし（SSH のベースライン）**：ワークベンチからラボ用インスタンスのプライベートアドレスの 22 番ポートを調べると open です。セキュリティグループには「22 ← ワークベンチ /32」のルールがあります。
- **Session Manager あり**：同じ調査がタイムアウト（filtered）になり、セキュリティグループには 22 を含む受信ルールが 1 つもなくなります。443 は影響を受けません。
- **どこで確認できるか**：比較レポートの `port22.open`、`sgRules22`。capabilities の shell-access の detail が「未启用」（未有効）から「无管理端口入站」（管理ポートの受信なし）に変わります。

### 監査の流れ（shell-access/session-audit、必須）

- **Session Manager あり**：セッション履歴（誰が、いつ）↔ セッションログ（何を実行したか）↔ CloudTrail の `StartSession`（IAM ID）をセッション ID で照合します。
- **比較**：SSH では journal から「公開鍵のフィンガープリント + 送信元 IP」しかわからず、「誰がどのコマンドを実行したか」には答えられません。

## プラットフォームモードについて

- プラットフォームのターミナルは独立したセッションドキュメント `ATL-SessionShell` を使い、このモジュールはそれを変更しません。セッションを数えるときはプラットフォームのターミナルのセッションを除外し、ワークベンチから開始したセッションだけを見ます。
- このモジュールが変更するのは、アカウント × リージョン単位のシングルトン `SSM-SessionManagerRunShell`（セッション設定）です。変更前に元の値を環境状態バケットにバックアップし、回収時に元に戻します。
- プラットフォームモードでは `scripts/module` の配信チャネルは最初から SSM なので、「配信方法が ssh から ssm に変わる」という観察ポイントはこのカードでは成り立ちません。
